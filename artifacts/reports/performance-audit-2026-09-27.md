# 归序性能测评与优化建议（2026-09-27）

## 范围与方法

- Windows 11，32 逻辑 CPU，31.7 GiB RAM。只读使用项目现有的 500、1,000、5,000 小文本文件数据集；数据库写入系统临时目录，测试结束后清理。未扫描、分类或移动用户照片。
- 使用 `scripts.run_phase_n_performance.run_size` 分别测扫描、SQLite 入库、会话文件关联、读取、工作区核对和进程 RSS；结果另存 `performance-audit-2026-09-27.json`。
- 对临时数据库中的 5,001 文件再次运行 `ConversationRepository.attach_files`，用 `cProfile` 拆解关联耗时。通过 Ollama 本机接口向 `qwen3-vl:4b-instruct` 发一条短文本和一张内存中生成的 256×256 JPEG，`max_tokens=80`，不使用个人媒体。
- 冻结包运行 `--diagnose` 三次；前端运行 `npm run test:run -- tests/ui-polish.test.ts`。诊断启动不是可见 WebView 的完整启动，jsdom 测试耗时不是浏览器帧率。

## 本轮实测

| 文件数 | 扫描 | 入库 | 关联到会话 | 读取会话文件 | 工作区核对 | RSS 增量 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 501 | 0.037 s | 0.056 s | 0.443 s | 0.004 s | 0.343 s | 12.2 MiB |
| 1,001 | 0.093 s | 0.108 s | 0.993 s | 0.007 s | 0.775 s | 12.1 MiB |
| 5,001 | 0.326 s | 0.643 s | 4.146 s | 0.059 s | 3.317 s | 48.5 MiB |

第一次 5,001 文件关联测得 32.183 s；同一数据的后续受控复测为 4.146 s，另一次 cProfile 运行 5.062 s。该差异可能受 Windows 文件缓存、防病毒扫描或系统负载影响，不能当作稳定回归。cProfile 的 5.062 s 中，文件 identity/哈希累计 2.429 s，路径范围校验累计 2.133 s；测试库中 5,001 条 `files.sha256` 均为空，因此需要逐文件补读。

本地 Ollama 简短文本请求 4.750 s（23 输入、7 输出 token）；随后合成图请求 1.108 s（1,051 输入、2 输出 token）。`ollama ps` 显示该模型约 3.5 GB、100% GPU；这些请求比应用真实规划/分批分类提示词短得多，不能推算 20 图整理总时长。冻结诊断 1.63/1.41/1.42 s，均 exit 0；`PeakWorkingSet64` 在进程退出后无法可靠读取，故不报告该内存值。前端 5,000 文件虚拟列表交互专项 3 passed，测试体 203 ms；这只证明 jsdom 下最多渲染 48 条并能搜到末项。

首次基准结束时，原脚本的 `PRAGMA integrity_check` 连接未关闭，Windows 临时文件清理报 `WinError 32`，命令 exit 1。已改为上下文管理的连接并重跑，第二次基准 exit 0、临时目录清理成功；旧的测试临时目录在进程退出后按精确路径清理。上述表格使用第二次结果。第一次报告被第二次结果覆盖，不将第一次命令记作通过。

## 优化优先级

1. **P1：减少首次关联的逐文件 I/O。** `ConversationRepository.attach_files` 对每项运行路径解析和缺失哈希补读，5,001 项占用约 4–5 s，冷态曾达 32 s。保留 reparse/scope 和执行前完整性约束的前提下，评估批量安全路径校验、在已有扫描/解析阶段持久化内容哈希，以及同一轮仅计算一次 fingerprint。先在有符号链接、重解析点、文件替换和竞态的安全测试上证明等价，再比较 500/1,000/5,000 项 p50/p95。
2. **P1：将打开会话的恢复核对改为更轻的增量写入。** 5,001 文件核对约 3.3 s；`WorkspaceReconciliationService.reconcile` 即使文件未变化也逐行 `UPDATE conversation_files`。建议先比较 size/mtime，仅对状态、路径或校验时间确需更新的记录写库；对重复切换会话作合并/取消，保留执行前强制核对。现有前端已经把核对放到后台，需测其 SQLite 写入对同时聊天/预览的影响。
3. **P1：大目录列表与方案预览分页。** 初始 `source-files` API 硬限 2,000 项，搜索也只能覆盖已加载项；当前文件列表有 48 条窗口化渲染，逐文件方案却将所有匹配条目一次性渲染。建议给源文件和方案操作加入服务端分页/搜索，并在方案列表做虚拟滚动。验收应覆盖 5,000 项真实 WebView 的首屏时间、输入延迟、内存和滚动帧率。
4. **P2：测真实模型全链再调批次。** 图片分类批次最多 4 张，20 张至少 5 个分类请求，另有规划、校验和可能的 repair。先记录每阶段耗时、每批图像像素/字节、token 和缓存命中；对本地 Qwen 用隔离合成照片测 batch 1/2/4 的总时长、VRAM 峰值、输出合约通过率。不要只为吞吐盲目增加并发，避免显存不足和错误重试。
5. **P2：补可观察的进度和取消。** 首次分析是较长的同步链路；在用户可见位置显示扫描、证据、规划、分类批次和预览的真实阶段，并允许安全取消/恢复。普通聊天模型调用仍缺 `model_calls` 时延/用量记录，先补审计再做基于数据的性能决策。
6. **P3：评估发行包体积与可选组件加载。** 便携 ZIP 约 144 MB，包内 OpenCV、FFmpeg、OCR/ONNX 等占据大部分体积。按功能剖析冷启动和实际使用，再考虑按需加载/拆分可选解析能力；必须保持生产缺失能力显式 unavailable，不能静默降级。

## 尚未测到

- 真实 Windows WebView 首屏、滚动 FPS、照片缩略图解码与高 DPI；本轮没有可见 UI 自动化数据。
- 本地 Qwen 处理真实 20 张约 12–16 MB 照片时的完整分析、分类准确率、重试率和峰值 VRAM；只做了合成图短请求。
- 长期运行、多会话切换的内存增长与并发 SQLite p95；本轮为短时单机基准。
